## 1. How NASSP embeds the AGC

NASSP compiles a modified copy of yaAGC's engine straight into each vessel
DLL. `Project/{Saturn5,Saturn1B,LEM}/CMakeLists.txt` list

    src_sys/yaAGC/agc_engine.c  agc_engine_init.c  agc_utilities.c
    src_sys/yaAGC/Backtrace.c   random.c           rfopen.c

(no SocketAPI.c, no agc_symtab.c). The engine calls back into the
vessel through five free functions defined in `src_sys/apolloguidance.cpp`
(:998-1046): `ChannelOutput` (every output-channel write and every
fictitious pulse channel), `ChannelInput` (returns 0: input is pushed,
not polled), `ChannelRoutine` (empty), `RequestRadarData` (radar cycle
complete: the vessel stores RNRAD) and `ShiftToDeda` (empty).

One `agc_t vagc` lives in the C++ class `ApolloGuidance`
(`src_sys/apolloguidance.h`), subclassed by `CSMcomputer`
(`src_csm/CSMcomputer.cpp`) and `LEMcomputer` (`src_lm/LEMcomputer.cpp`).
Saturn5.dll / Saturn1B.dll hold the CMC, LEM.dll the LGC: one AGC per DLL
per vessel instance, so a library with static state (ours) is fine for
one CSM + one LM per scenario (two Saturn vessels in one scenario would
share one CMC: never the case for Apollo 11).

Stepping: `CSMcomputer::agcTimestep` / `LEMcomputer::agcTimestep` compute
`(simt - LastCycled) / 11.71875 us` and call `agc_engine(&vagc)` that many
times per Orbiter frame (about 85,333 calls per simulated second), calling
the PCM telemetry `TimeStep` every 0.15625 ms in between. With
multithreading and time acceleration > 1 the same loop runs in a worker
thread under `agcCycleMutex`. Before the first step the CMC sets TIME2/TIME1
from TEPHEM and the Orbiter MJD (`CSMcomputer.cpp:209-234`, "PadLoaded").
When unpowered, both computers clear A, L, Q, EB, FB, BB, set Z = 04000,
clear the interrupt state, and do not step (`CSMcomputer.cpp:139-206`,
`LEMcomputer.cpp:120-185`): a power cycle is a GOJAM.

DOWNRUPT is not generated by the engine (commented out, "DS20060402"):
the PCM telemetry raises it (`csm_telecom.cpp:3312, 3558, 4154`,
`lm_telecom.cpp:813`) and reads channels 034/035 itself.

### 2d. Uplinks (MCC -> AGC)

MCC builds DSKY key strings (`mcc.cpp` CM_uplink / LM_uplink) and the
telecom sends them as INLINK words with UPRUPT, one per 0.1 s, waiting
while UPRUPT is pending (`csm_telecom.cpp:4945`). The P27 verbs used:
V71 block loads to 1501 (UPSVFLAG + RRECT/VRECT/TET: state vectors, 21
words), 1735 / 1733 (REFSMMAT), 306 / 3606 (XSMD), 3400 (entry target,
16), 2022 (RLS), 2400 (TLAND); V72 scatter loads (rtcc.cpp:30057, 40935);
V70 liftoff time; V73 clock. So V71/V72 must land in the typed erasable
for the uplinks to mean anything (see 3).

## 3. The erasable map (critical path)

Our erasable is typed and owned by modules; `src/core/ecadr.c` maps only
the flagwords (074-0111) and keeps a raw image for everything else
(DEVIATION). Classification of what NASSP and its uplinks touch:

| class | addresses | status | needed |
|---|---|---|---|
| A. counters / timers | 024-025 TIME2/1, 032-036 CDUs, 037-041 PIPAs, 042-044 RHC, 045 INLINK, 046 RNRAD, 047 GYROCTR, 050-052 CDUxCMD, 053-054 CDUT/SCMD, 055 THRUST, 060 ALTM | accessors exist (state.h, imu.h, exec.h TIME3-6) | shim maps them directly (no ECADR change) |
| B. flagwords | 074-0111 (FLAGWRD8 0104 = MOONFLAG) | ECADR map exists | none |
| C. named pad/uplink erasables with an accessor | REFSMMAT, TEPHEM, RRECTCSM/VRECTCSM/TETCSM, RRECTLEM/.., RLS, TLAND, CSMMASS, LEMMASS, DAPDATR1/2, UPSVFLAG, CDUCHKWD, RTED1, P37RANGE | accessor in state.h | ECADR map entries (word <-> typed value) |
| D. named, module-private | IMU compensation (imu/compensation.c), ephemeris (nav/auxiliary/ephemerides.c), AZO/AXO/-AYO/504LM (planetary.c), LAUNCHAZ/LATITUDE/AZIMUTH (csm/prelaunch), TVC filter/DAP (csm/dap/tvc), entry pads, Saturn takeover, landing targets (lm/landing), RRECT/VRECT/TET working set (nav/integration ctx), XSMD | storage exists, no address | per-module ECADR word handlers |
| E. no C equivalent | A, L, Q, EB, FB, Z, BB, VAC areas, core sets, waitlist LST1/LST2, phase tables, RUPTREG, ITEMP/EXECTEM (CMPAD 0075/0077/0104/0110/0333 are zeros or flags-as-temps) | hardware or executive internals | ignored; documented |

Mission scenarios ("Apollo 11 - 02 - Insertion" ...) store class E as
well, so a running program cannot be restored from them; the shim imports
classes A-D, then does a restart (GOJAM -> GOPROG, i.e. P00 with the
navigation state kept) and the program is reselected (V37) as after a
restart. That is the documented save/restore deviation.

## 4. Shim design

NASSP's own `src_sys/yaAGC/agc_engine.h` is kept (the C++ includes it via
`"yaAGC/agc_engine.h"` relative to src_sys/, so it cannot be swapped by an
include path); only the six yaAGC .c files are replaced by our
`src/nassp/engine.c`, compiled against that header, plus libagc and
src/sim's clock.c, channels.c, counters.c, rope.c. So NASSP's C++
compiles unchanged; the one NASSP edit is the CMake source list (option
`NASSP_AGC_BACKEND=apollo-c`).

- `agc_engine_init` / `agc_load_binfile`: vehicle from the rope name
  (Comanche055 / Luminary099), agc_power_on, rope for ROPECHK.
- `agc_engine`: counts MCTs; every 26 2/3 MCT (one 1/3200 s scaler count)
  runs one scaler count of src/sim clock.c (counters, interrupts, the
  executive). Inputs written by NASSP into `vagc` between steps
  (InputChannel, InterruptRequests, Erasable mirror) are imported first;
  outputs are exported to `vagc` and sent through `ChannelOutput`.
- The `vagc.Erasable` image is a mirror: classes A-D exported after each
  scaler count; NASSP's writes detected against a shadow copy and
  imported through the class A accessors or `agc_erase_write_ecadr`.
- `sim_socket_send` (the peripheral hook of src/sim) becomes ChannelOutput
  with NASSP's channel numbering (0171/0172 -> 0141/0140; 0142/0143 added).
- DOWNRUPT: external (NASSP's PCM), so the sim clock's free-running
  DOWNRUPT is switched off in this build.
- Power: Z == 04000 written by NASSP's power-off code = GOJAM on the next
  powered step.

Not compatible (needs no NASSP edit, only documented): the engine flags
saved in STATE / CYCLECOUNTER are meaningless for us; MakeCoreDump writes
nothing; `vagc.InIsr` / `InterruptRequests[0]` report the interrupt being
serviced only for the duration of a scaler count.

## 5. Build and run plan (host via WSL interop)

- Toolchain: VS 2022 Build Tools 14.44 (cl 19.44), CMake 4.4, generator
  "Visual Studio 17 2022" -A x64, config RelWithDebInfo. Configure with
  `-DORBITER_INSTALL_DIR=C:/NASSP9-dev -DFINAL_INSTALL_DIR=C:/NASSP9-dev`:
  the DLLs land directly in `C:\NASSP9-dev\Modules\ProjectApollo`
  (MFDs in Modules\Plugin). Drivers: `C:\Users\cnama\nassp-work\*.bat`.
- libagc on Windows: our C11 sources compiled by the same CMake (a static
  library target added by the patch from `APOLLO_C_DIR`), MSVC /std:c11.
- Run: `C:\NASSP9-dev\Orbiter_ng.exe -s "Project Apollo - NASSP\<scenario>" -T <s>`
  (Orbiter.exe options: -s launch and exit on close, -T terminate after
  <s> system seconds, -t at a simulation time, -f fixed step). Orbiter_ng
  starts `Modules\Server\Orbiter.exe` and exits: wait on that process.
  On exit Orbiter writes `Scenarios\(Current state).scn` with the AGC
  section and the DSKY state: the comparison artefact against the stock
  run of the same scenario and duration.
- Scripting: the Saturn vessel exposes Lua (`get_agcerasable`,
  `set_agcerasable`, `get_agcchannel`, panel switch get/set); the LEM in
  NASSP 9 exposes none (correction, 2026-10-13: LEM has no clbkGeneric /
  Lua_InitInstance). Test hook sim/nassp/patches/0002-lem-lua-test-interface.patch
  gives the LEM the same four read/press methods (get/set_panelswitch,
  get_agcerasable, get_agcchannel; no set_agcerasable, no behaviour change:
  only a Lua binding and the Lua link library), plus two hand-controller
  inputs for the landing (2026-10-13): set_ttca_throttle (the TTCA throttle
  position, as the throttle keys move it) and set_agcinputbit (an LGC input
  bit, as LEM.cpp's ROD keys and VESIM buttons set channel 016 bits 6/7,
  KEYRUPT2 on a set bit). It is applied to BOTH
  sides of every LM comparison: the reference LEM.dll in C:\NASSP9-ref is
  built from stock source 5470bf1 + 0002 (yaAGC engine); ours is built
  from 0001 + 0002. C:\NASSP9 (the release install) is never modified. The
  Checklist MFD can auto-execute checklist items; MCC (the "MCC" vessel)
  runs ground tasks and uplinks by itself in its mission state machine.
  What a person must do: Orbiter has no key-injection API for the DSKY,
  so DSKY entries come from the checklists (auto) or a Lua script.

Milestones and verification: each against the stock C:\NASSP9 run of the
same mission scenario (`Scenarios\Project Apollo - NASSP\Apollo - Mission
Scenarios\Apollo 11\01..15`), compared on the saved (Current state)
scenario: DSKY PROG/VERB/NOUN, REFSMMAT, state vectors, TEPHEM, the
vessel's orbit, and the MCC state.

## 6. Effort and risks

- Erasable map (class C/D): ~500 named words over two ropes; the first
  milestones (launch, P11) need about 30 (TEPHEM, IMU compensation,
  LAUNCHAZ/LATITUDE/AZIMUTH, masses, DAP data), the burns ~60 more, the
  landing the LM W-matrix and targets. Days of work, done per milestone.
- Uplink: V71/V72 stores into the raw ECADR image today (ecadr.c
  DEVIATION), so MCC state-vector / REFSMMAT / target uplinks do not reach
  the programs until class C/D addresses are mapped. This is a flight-code
  gap that also affects agc_sim.
- Save/restore: mission scenarios restore only the navigation state, not
  a running program (section 3).
- Timing: NASSP steps per MCT; our jobs run in zero time at scaler-count
  granularity, as in agc_sim. The PCM downlink reads 034/035 after its own
  DOWNRUPT; served at the next scaler count (<= 0.3125 ms).
- Fidelity of NASSP's hardware models assumes yaAGC's burst rates (CDU
  drive bursts every 600 ms / COARSE_SMOOTH): ours are 24 pulses per 75 ms.
